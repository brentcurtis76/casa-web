## [B1] BLOCKING — the gate reports a clean pass when a tool did not run at all

`changed-files-diagnostics.sh` swallows tool failure. `readJson()` catches every parse
error and returns `null`, which becomes `[]`; if `tsc` fails to start, `tsc.txt` simply
contains no header lines and yields zero diagnostics. Nothing is written to stderr and the
exit code stays 0.

The PM demonstrated it. Running the script with `deno` (and the project's `npx` toolchain)
absent from `PATH`:

```
$ env PATH="$(dirname $(which node)):/usr/bin:/bin" \
    bash scripts/gates/changed-files-diagnostics.sh supabase/functions/create-mesa-matches/index.ts
EXIT=0
=== supabase/functions/create-mesa-matches/index.ts
--- tsc (0)
--- eslint (0)
--- deno lint (0)
--- deno check (0)
(stderr: empty)
```

That same file's real baseline is `deno lint (4)` and `deno check (6)`.

**Why this blocks.** D8's criterion is *"cero diagnósticos **nuevos**"*. A run that emits
all zeros has, trivially, no new diagnostics — so a broken toolchain does not fail the
gate, it **passes** it, silently, for every phase P1–P8. This is the same false-negative
class that Z5b exists to exclude: Z5b proves the gate detects a substitution *when the
tools run*, and nothing yet proves they ran.

**The plan already anticipates the mitigation** and the script does not implement it —
`PLAN.md` D8, point 5:

> Los recuentos globales (`tsc` 1041, ESLint 160, `deno lint` 94, `deno check` 46) se
> registran en el reporte **como observación**, no como criterio: sirven para detectar
> sorpresas, no para aprobar.

The script emits no global counts, so there is nothing for a reviewer to notice the
surprise with.

### What to change

1. **Emit the four global totals on `stderr`** — every run, unconditionally. Format is
   yours; something like
   `[gates] totales del proyecto: tsc=1041 eslint=160 deno-lint=94 deno-check=46`.
   **They must go to stderr, not stdout.** `stdout` is the artifact that gets diffed
   between the parent phase and the branch tip; putting counts there would inject a noisy
   diff line into every comparison and would invalidate the committed baseline. Keeping
   them on stderr makes them exactly what D8 point 5 asks for — an observation.
2. **Fail loudly instead of returning zero.** For each of the four tools, if it produced
   **no attributable diagnostics at all across the whole project**, or its JSON is
   unparseable, write a clear diagnostic to stderr naming the tool, include the tool's
   captured stderr, and **exit non-zero**. Every one of the four has a large, non-zero
   baseline in this repo (1041 / 160 / 94 / 46) and fixing them is an explicit non-goal of
   this workstream, so a global zero from any tool means the tool did not run — it never
   means the repo got clean. Record that reasoning as a declared assumption in the README,
   the same way round 1 declared the `deno check` multi-frame limitation.
3. **Document both in `scripts/gates/README.md`**, under a new heading. Say plainly what
   the failure mode was and why a gate that can silently return zero is worse than no gate.

### What NOT to change

- Do not alter what goes to **stdout**. The committed `base-by-file.txt` must stay valid.
- Do not touch the attribution logic, the sorting, the `deno check` grouping, or the path
  normalisation. They were verified and they are correct.
- Do not regenerate `base-by-file.txt`. Criterion R3 below proves it does not need it.
