## [B1] BLOCKING — a clean tool run is misclassified as "the tool did not run"

`scripts/gates/changed-files-diagnostics.sh:165`:

```js
const failed = TOOLS.filter((t) => parseErrors.has(t) || totals[t] === 0);
```

Codex reproduced the false positive: it ran all four command boundaries with **valid,
parseable, successful, zero-diagnostic** output. Every command exited 0 — and the gate
exited 1 and reported all four tools as failed.

**Why it blocks.** The inference "zero global diagnostics ⇒ the tool did not run" is
invalid, and it violates frozen decision **D8 point 5** (`PLAN.md:252`), which says the
global counts are an **observation**, explicitly *"no como criterio"*. Round 2 turned zero
into an approval criterion. The README at `:176` even acknowledges the false-positive
condition and defers it until the repo becomes clean — deferring a known wrong inference is
not the same as being right.

For the record: round 2 was solving a real problem (round 1's script exited 0 with all
zeros when `deno` was missing, so a broken toolchain **passed** the gate). That problem is
real and must stay solved. The defect is the **discriminator**, not the goal.

### The fix Codex specified

Capture each tool's **exit status** at the command boundary and pass it into the
attribution step, then classify on (exit status, output validity, diagnostic count) rather
than on count alone:

- zero diagnostics **+ the command succeeded with valid/empty-but-well-formed output**
  → **legitimate clean run**. Not a failure. Exit 0.
- zero diagnostics **+ the command failed, or its output is unparseable/malformed**
  → **tool failure**. Name it on stderr with its captured stderr, exit non-zero.
- the tool's normal "I found problems" exit **+ usable diagnostics** → normal
  baseline-red execution. Exit 0. This is what every real run in this repo looks like.

The global totals **stay on stderr on every run**, exactly as they are now — that part is
D8's observation and Codex did not object to it.

Notes on the four boundaries, so you classify correctly:

- `npx tsc -p tsconfig.app.json --noEmit` — exit 0 when clean, non-zero when it reports
  errors, 127 when the binary is missing.
- `npx eslint . -f json` — exit 0 when there is nothing to report, 1 when there are lint
  errors, 2 on a fatal config error. **A clean run prints `[]`, which is valid JSON** — so
  for the two JSON tools, "the output parses into the expected shape" is the strongest
  single signal that the tool ran, and an empty array/empty diagnostics list is a
  legitimate result.
- `deno lint --json` — a clean run prints `{"version":1,"diagnostics":[]}`.
- `deno check .` — exit 0 when clean, non-zero when it type-checks with errors, 127 when
  missing. No JSON mode, so exit status carries more of the weight here.

Use whichever combination of these signals you can defend; the criteria below are what
must hold, not a required implementation.
