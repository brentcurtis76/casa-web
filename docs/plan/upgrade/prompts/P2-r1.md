## D5 — THE ELEVEN GUARANTEES. This is the contract.

`balanceMainDishCarriers` is a **bounded local search**. The plan freezes *what must hold*, not
how you traverse. Each of these is a property you must establish:

1. **Never** assign `main_course` to a carrier with `canBringMainDish === false`.
2. Hosts **never** move between tables.
3. Every swap preserves **exactly** the number of people at each table involved (you swap
   guest subsets of ≤2 elements with equal people-sums).
4. After any swap, each table's guest units still satisfy `≤ maxGuestUnits`.
5. No swap leaves the **donor** table in deficit.
6. **Every applied swap reduces total deficit by at least 1.**
7. The process **terminates**: by (6) and because total deficit is an integer `≥ 0`, at most
   `Δ₀` swaps are applied, `Δ₀` being the initial deficit.
8. **Each table assigns exactly `min(requiredMains, willingCarriers)` main dishes after
   rebalancing.** Without this, an implementation could under-assign and simply report a larger
   deficit — satisfying everything else and still being wrong.
9. **The global participant set is preserved**: after rebalancing, the union of all tables'
   guests is exactly the input's, **with no duplicates and no losses**. This code has already
   had a bug of this class — the comment at `create-mesa-matches/index.ts:305` documents fixing
   "one guest at two dinners".
10. Every table under quota appears in `tablesWithShortfall` with its `shortfall`.
11. For the same input and the same `pick`, **this** implementation always produces the same
    result. Internal determinism only — **no** equivalence with any other hypothetical
    implementation is required, and none may be asserted.

**What the plan deliberately does NOT fix, and you decide:** the order in which deficit tables
and donor tables are traversed, the order of subset enumeration, the order of `SIDE_FOODS`, and
the exact sequence of `pick` calls. A traversal that only looks at the first deficit table can
stop early — that is why guarantee 10 requires reporting the real deficit and why **no
guarantee demands exhaustiveness**. If your traversal improves on that, good; the plan neither
requires nor forbids it.

### How the guarantees get established — read this before writing a single test

The plan is explicit that examples do not prove a "never". Three mechanisms, and **claim
nothing beyond them**:

- **A reusable invariant verifier** in the test file, applied to the result **and to every
  returned move**, checking guarantees 1–6, 8 and 9. **Every** allocation and rebalancing test
  calls it, so each new case re-validates all of them.
- **A table of boundary and adversarial fixtures** — a table with no willing carriers, all
  willing, capacity at the limit, simultaneous deficits across several tables, `+1`s on both
  sides — not a single happy path.
- **Code review of the loop invariant** for guarantee 6, which no finite set of examples can
  establish. In your report, quote the acceptance condition of the swap and show that it
  requires strict decrease.
