### The four tools, verified working in this repo today

| Tool | Command | Run from | Notes |
|---|---|---|---|
| tsc | `npx tsc -p tsconfig.app.json --noEmit` | repo root | Emits `path(line,col): error TSxxxx: message`. Paths are repo-relative. |
| ESLint | `npx eslint . -f json` | repo root | **`-f json`, never `npm run lint -f json`** — npm eats `-f` as `--force` (criterion Z2). `filePath` in the JSON is **absolute**; you must relativise it to match the caller's argument. |
| deno lint | `deno lint --json` | `supabase/functions/` | `diagnostics[].filename` is a `file://` URL. |
| deno check | `deno check .` | `supabase/functions/` | Text only, no JSON mode. |

I verified all four run and produce the shapes above on `19c44aa` with Node v22.22.0,
npm eslint v9.39.2, TypeScript 5.9.2, Deno 2.7.11.

### Hazards I have already confirmed — handle these, they are not hypothetical

- **All four tools exit non-zero** when they find problems (they always will here). A bare
  `set -e` will kill the script on the first tool. Guard every invocation.
- **`deno check` writes ANSI colour escapes** even through a pipe. I checked: its output
  contains `\033[36m` etc. Set `NO_COLOR=1` and/or strip escapes, or the "raw message"
  comparison will diff on colour codes.
- **`deno check` diagnostics are multi-line**: the message comes first and the
  `at file:///…:line:col` location comes several lines later. Naive `grep <path>` gives
  you the location line without the message. Decide a grouping and document it in the
  README; if a clean grouping is not achievable with the installed Deno, say so under
  ASSUMPTIONS and emit the location lines with whatever context you can attribute — but
  **do not silently emit something that looks complete and is not**.
- **`deno lint`/`deno check` only see `supabase/functions/`; `tsc`/ESLint only see the
  Vite app.** A file will legitimately have zero diagnostics from two of the four tools.
  Print the `--- tool (0)` line anyway; a missing section reads as a bug.
- **Running all four per invocation is fine.** They are whole-project tools; run each
  **once** per script invocation and filter the single output to all requested paths. Do
  not run tsc once per file.
- **A path that does not exist must not crash the script.** Later phases will pass paths
  for files that do not exist yet in the parent commit (P2's `mainDish.ts`, P8's
  `dinnerSummary.ts`, …). Emit the file header with zero counts for all four tools.
- Determinism (Z4): sort within each tool section, and do not embed timestamps, absolute
  paths, hostnames, PIDs, or elapsed times anywhere in the output.
